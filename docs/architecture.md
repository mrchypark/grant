# Grant architecture

Grant is a Go 1.27.3 service with a concrete `Service` and `Store` in `internal/grant`. `internal/api` owns the HTTP boundary. Four `cmd` packages provide the `grant` server and migration commands, the canonical Patch Data manifest digest tool, the management catalog generator, and the Patch Data catalog generator. Storage calls Rhiza v0.21.2's native Go API and does not require cgo.

The application preserves the organization, identity, membership, provider, action, role-binding, application-consent, authority-import and HTTP-capability contracts from baseline `c716877`. The [HTTP inventory](porting-go-http-contract.md) records method/path/authentication boundaries. All public authorization endpoints retain coarse allow/deny semantics and reject the presence of `resource.view`, including null. Historical field-view rows remain guarded by fail-closed startup validation.

Canonical mutations use native atomic execution with statement expectations. Bulk authority imports retain a single transaction even when entity count exceeds the native statement-count limit. Shared canonical hashing functions are used by the API and the manifest and catalog tools. Imported authority ownership and generation/replay checks must remain intact across migration.

Each native voter has a local materialized store and participates in the shared durable object-store topology. Strong reads use the native linearizable path. Remote SQL is an authenticated separate private listener; public API credentials cannot authorize it. Kubernetes peers use UDP QUIC and fixed member identities.

Learner reads retain a fresh per-request quorum fence: the learner catches up to at least that fence, and each decision uses one pinned applied snapshot. Fence acquisition or catch-up failure, or a snapshot that remains unstable after bounded retries, fails closed. The local performance comparison did not establish a consistent benefit from removing this freshness guarantee; an unfenced stale snapshot can still allow an action after its permission is revoked.

## Independent authorization scope assessment

Before implementing an application request, assess whether its authorization requirement can be expressed and enforced through a reusable contract. This is a scope decision, not a claim that the requested integration is implemented or verified. Record the principal and organization/application context, action/resource mapping, trusted evidence source, enforcement point, and failure behavior. Admission requires an unambiguous mapping to policy inputs, binding of the decision to the actual request (and response where needed), and fail-closed enforcement without an unguarded upstream path. Missing evidence or unsupported semantics must remain an explicit gap until the contract and enforcement can support them; application-specific meaning must not be inferred from route or field names.

| Owner | Responsibility |
| --- | --- |
| Grant | Own policy evaluation, admission checks (including membership, application scope and consent), allow/deny decisions, and the public authorization contract. Validate catalog, principal and request bindings; do not infer business meaning or independently reconstruct HTTP bodies from Exposure's descriptors. |
| Exposure | Capture the actual HTTP request and relevant response evidence, canonicalize it under the declared contract, extract and bind authorization inputs, and enforce Grant's decision before forwarding requests or releasing protected responses. Reject unsupported or ambiguous evidence and unavailable decisions. |
| Identity provider (IdP) | Own authentication and identity assertions. Verified identity supplies policy input; authentication alone does not grant application or resource access. |
| Application owner | Define business actions, resource identities, ownership/relationship semantics, and their explicit catalog/policy mappings, including safe list fields and response relations. Establish that the upstream behavior matches those mappings. |

A learner is an execution mode for the same authorization semantics, not a separate policy model or a relaxation of freshness. The quorum fence and pinned snapshot requirements in [runtime modes](runtime-modes.md) still apply. A requested workspace header is initially application context: assess its trust source, resource mapping and binding under the [HTTP capability contract](http-capabilities.md) before deciding whether a generic contract extension is needed; its presence does not automatically make workspace support a Grant feature. A bootstrap helper belongs to generic deployment tooling and must use explicit provisioning contracts rather than introduce application-specific authorization behavior. Independent authorization scope acceptance does not require an RPO-zero gate; durability and recovery requirements are separate deployment assessments and must not be inferred from authorization freshness.
